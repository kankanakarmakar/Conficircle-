# ConfCircle Backend — Complete Walkthrough (Beginner-Friendly)

This document explains **every folder and every file** that was created in
`backend/`, why it exists, and what it does. It is written for someone who
has **never worked with microservices or NestJS** before. Read it top to
bottom once, then keep it as a reference map.

---

## Part 0 — The 5-minute crash course

Before the file list, you need the core idea. You already know how one
app works (your Flutter app is one big program: UI + logic + data all in
one place). That style is called a **monolith**.

### What is a microservice?

A microservice is the opposite: you split the work into **many small
independent programs**, which talk to each other over the network.
Conceptually:

```
                        INTERNET
                           │
                ┌──────────▼──────────┐
                │     API Gateway     │   ← the only door (3000)
                │  doorman + router   │
                └──┬─────┬─────┬─────┘
        ┌──────────┘     │     └──────────┐
        │                │                │
 Identity             Content        Assessment   Progress
   │                    │                │            │
 identity            content          assessment     progress   (schemas)
```

- Each "box" (service) is its **own full program** with its own HTTP
  server, its own database, and its own Dockerfile. It can be built,
  started, restarted, and deployed **independently**.
- If the Progress service crashes, identity/content/assessment keep
  running. If you rewrite the content service, you never touch the
  auth code.
- **API Gateway** = one public address (`:3000`). The Flutter app only
  ever talks to it. It can't reach the internal services directly.

When does a service talk to another service? Sometimes via HTTP
(request-response), sometimes via **events** (fire a message on a bus and
forget). We use RabbitMQ for events, described below.

### A service is like a small Flutter project

NestJS (our Node.js backend framework) is conceptually like Flutter:
it uses **modules** to organize features, **controllers** (like widgets
that listen), **services/providers** (like your `ChangeNotifier`
providers — reusable logic), and **dependency injection** (like Flutter's
`context.read<T>()` — "give me the thing I need, I don't build it").

### Mapping to what you already know

| Flutter concept | Backend (NestJS) concept || --- | --- |
| `main.dart` | `src/main.ts` — boot the app |
| `MaterialApp` + `providers: []` | `src/app.module.ts` — wire modules together |
| `ChangeNotifier` | a Nest `@Injectable()` service |
| route + screen | controller + endpoint |
| `pubspec.yaml` | `package.json` |
| shared_preferences | Redis (server-side "fast memory") |
| local SQLite-ish storage | PostgreSQL (+ Prisma ORM) |
| — | Docker Compose (runs the backend "machines") |

## Part 1 — `backend/` root files

```
backend/
├── package.json           ← root package.json
├── pnpm-workspace.yaml    ← tells pnpm this is a monorepo
├── pnpm-lock.yaml         ← exact dependency versions lockfile
├── tsconfig.base.json     ← shared TypeScript rules
├── docker-compose.yml     ← runs PG + Redis + RabbitMQ
├── .env.example           ← template env vars (safe to commit)
├── .env                   ← YOUR real env vars (gitignored, never commit!)
├── backend/.gitignore     ← things git must ignore inside backend/
├── README.md              ← how to run the backend
└── pnpm-build-state/...   ← (auto-generated by pnpm, ignore it)
```

### `package.json` (root)

- `name: "@conficircle/backend"` — the root is a private "meta package".
- `scripts` at the root let you run one command for ALL apps:
  - `pnpm build` → builds all 5 services + 4 packages
  - `pnpm start` → attempts to start all
  - `pnpm test` → runs tests of every app
  - `pnpm infra:up / infra:down` → start/stop Docker infra
- `devDependencies` held centrally: `typescript`, `prisma`, `jest`,
  `ts-jest`, `@types/node` — so every app shares ONE compiler and ONE
  test runner.
- `pnpm.onlyBuiltDependencies` — a security allowlist: for which packages
  the install step is allowed to run "postinstall" scripts
  (Prisma's engine download). Without it pnpm refuses and prints a
  warning (scripts can run arbitrary code during install!).
- `packageManager: "pnpm@12.16.1"` — pins the version of pnpm so any
  teammate's machine behaves identically.

### `pnpm-workspace.yaml`

```yaml
packages:
  - "apps/*"        # api-gateway, identity-service, ...
  - "packages/*"    # contracts, event-schemas, logger, configuration
```

This single flag turns the folder into a workspace. Consequences:

1. Node modules are shared between apps (not five copies of Express).
2. Apps can import each other and the packages by name:
   `"@conficircle/logger": "workspace:*"` means "from this repo".
3. `pnpm --filter @conficircle/identity-service build` targets one app.

That's what makes this a "monorepo": one git repo, many independently
buildable programs.

### `tsconfig.base.json`

TypeScript is JavaScript with types and compiles down to JS. This file
defines **shared compile rules** for everything:

- `"target": "ES2022"` — modern JS output
- `"strict": true` — catch type bugs at compile time (like Dart's strict
  types but stricter)
- `emitDecoratorMetadata` + `experimentalDecorators` — required by NestJS
  so your `@Module`, `@Controller`, `@Injectable()` classes can carry
  runtime metadata
- `outDir: dist` — compiled JS goes to `dist/`

Every app and package has a small `tsconfig.json` that `extends` this
file; each one only adds its specific paths.

### `docker-compose.yml`

Docker Compose is a script that describes how to run several Docker
containers so a single command (`docker compose up -d`) starts them all.
We run 3 machines (Phase 7):

| Container | Image | Port on your machine | Purpose |
| --- | --- | --- | --- |
| `conficircle-postgres` | `postgres:16.2` | `127.0.0.1:14332` | 4 databases |
| `conficircle-redis` | `redis:7.2` | `127.0.0.1:16379` | fast memory cache |
| `conficircle-rabbitmq` | `rabbitmq:3.13` | `127.0.0.1:56780` (+ UI 15690) | event bus |

Important things inside the file (read with comments):

- `restart: unless-stopped` — if the machine crashes, Docker restarts it.
- **Volumes** (`postgres-data`, `redis-data`, `rabbitmq-data`) — if you
  `docker compose down`, data is preserved; `docker compose down -v`
  also deletes volumes (wipes databases).
- **Health checks** — `pg_isready`, `redis-cli ping` etc. show Healthy in
  `docker compose ps`; used with monitoring later.
- **Bind to 127.0.0.1 only.** The pg/redis/rabbit ports are bound to
  `localhost`, so nothing outside your machine can scan them.
- Non-standard host ports, because 5432/6379/5672 already exist on this
  workstation from other projects. Container-interior ports stay
  standard; the mappings are controlled in `.env`.
- Credentials come from `.env` via `${VARIABLE:?...}` — the file refuses
  to start if vars are missing (a footgun turned loud).

### `.env.example` / `.env`

Every app needs secrets/addresses at runtime. `.env.example` documents
every variable and what it does (with fake values) and is committed.
`.env` holds real values and is **gitignored**; never commit it.

See Part 4 for a full per-variable explanation.

### `.gitignore` (backend)

Prevents `node_modules/`, `dist/`, `.env`, coverage, and logs from
entering git.

### `README.md`

Quick-start: prerequisites, install, infra, build, run, health check,
commands table. If you forget anything, start there.

│   ├── app/health/         ← mandatory health endpoint

│   │   ├── rabbitmq.service.ts
│   │   ├── rabbit.module.ts
│   │   ├── publisher/      ← "we send events"
│   │   └── consumer/       ← "we receive events"
│   └── modules/            ← ACTUAL BUSINESS FEATURES go here
│                              (mostly empty right now by design)
├── test/

### The five services and ONE-LINE summaries

| Service | Port | Purpose | Extra |
| --- | --- | --- | --- |
| `api-gateway` | 3000 | THE DOOR: Flutter only talks to this. Routes, guards, rate limits, Swagger `/docs`. | has `modules/proxy/` (dev-only relay until real controllers) |
| `identity-service` | 3001 | users, email/password, tokens, refresh rotation, guest accounts | owns `identity` schema |
| `content-service` | 3002 | topics, questions, quick tips, videos, resources, publication flow | owns `content` schema |
| `assessment-service` | 3003 | assessments, attempts, responses, server-side scoring | owns `assessment` schema; scoring never leaks |
| `progress-service` | 3004 | what users did: history, video position, daily stats, dashboards | owns `progress` schema |

Why 5? Because they change at different rates and have different data:
auth rarely changes but must be rock-solid; content CRUD is dynamic;
scoring is math-heavy and must never cheat; dashboards are read-heavy.
By splitting them, one change doesn't risk the others.

### The same code, explained

#### `src/main.ts` — that app's `main.dart`

Bootstrap: creates the NestJS server, adds validation pipes (global
input validation), CORS, and calls `app.listen(PORT)`. Each service
reads its port from env; gateway is `PORT=3000`, others 3001–3004.

- The 4 domain services also register a `ValidationPipe` on the whole
  app and a graceful `enableShutdownHooks()` (handles CTRL-C cleanly).
- The gateway additionally:
  - attaches the `CorrelationIdMiddleware` (gives each request an ID)
  - registers a global `GlobalExceptionFilter` (no stack leaks in prod)
  - builds **Swagger** docs at `/docs`

#### `src/app.module.ts` — the main root-like layout where we wire

NestJS apps are built of modules. The root module imports the pieces:

```ts
imports: [HealthModule, PublisherModule, ConsumerModule, RabbitModule.forRoot(...)],
```

Everything is "declared" here so Nest can build it. Providers listed at
the top-level of `@Module({...})` are like `ScreenState`s with
`MultiProvider` (Flutter keyword): one instance, injected everywhere.

#### `src/config/config.ts` — env → typed values

```ts
async function loadConfig(env): AppConfig;
```

- reads `PORT`, `NODE_ENV`, `LOG_LEVEL`, `RABBITMQ_URL`, `DATABASE_URL`
- falls back to sane defaults
- **fails fast** with a clear error at startup instead of undefined
  values crashing later
- gateway has `corsOrigins()` and `upstreamRoutes()` helpers in the same
  file (it has no database).

#### `src/health/*` — mandatory lifespan checks

`health.controller.ts` + `health.module.ts` create `GET /health` that
returns `{status:"ok", service:"...", timestamp:"..."}`.
Orchestrators (docker, k8s, load balancers) poll this to know if an app
is alive. Each app gets a customizable `createHealthModule(...)`
(currently a simple static controller, one per service).

#### `src/common/*` — cross-cutting pieces

These belong to every app because they "wrap" all incoming requests:

- `correlation-id.middleware.ts` — for debugging, when a user complains,
  find the exact log line by `x-request-id`. Gateway generates/forwards
  it.
- `global-exception.filter.ts` — "when ANYTHING throws, wrap it": JSON,
  correct status code, correlation ID, no stack trace in response.
- `jwt-auth.guard.ts` — **STUB today**: real JWT verify lands in Phase 8.
  It can either pass through (dev mode) or reject missing `Bearer`
  tokens when `REQUIRE_AUTH=true`, but nothing verifies signatures yet.

Nest middlewares vs Flutter analogy: runs on every request like a
`WidgetsApp.builder` wrapping every page.

#### `src/messaging/*` — like your `Firebase Messaging` abstraction, but RabbitMQ

Three weird-looking pieces. One by one:

- **`rabbitmq.service.ts`** — talks to RabbitMQ. Real, complete code.
  Connects lazily, asserts a **topic exchange** called `conficircle.events`.
  - `publish(eventType, payload)` → sends a message ("fire and forget").
  - `consume({queue, routingKeys, handler, maxRetries})` → subscribes;
     when a message arrives, run `handler`; if it throws 3 times →
     send to **dead-letter queue** (`<queue>.dlq`) and never retry
     again (prevents infinite poison messages).
- **`rabbit.module.ts`** — makes one RabbitMQService available everywhere
  via dependency injection (`RABBIT_TOKEN`). Like registering one
  Firestore singleton and `context.read`ing it anywhere.
- **`publisher/publisher.module.ts`** and **`consumer/consumer.module.ts`**
  — conceptual split. Code that EMITS events lives in publisher; code
  that REACTS to events lives in consumer. Keeping them apart keeps
  service logic from leaking event details.

Why events at all? Microservices avoid calling each other for things
like "user registered ⇒ create empty dashboard row". They fire
`identity.user.registered` and whatever service cares, reacts. This
loosens coupling: progress-service can be offline and catch up because
RabbitMQ holds the message.

#### `src/modules/*` — WHERE FUTURE CODE WILL LIVE

Today only `api-gateway/src/modules/proxy/proxy.controller.ts` exists
(dev relay). In Phase 3 you'll see folders like:

- `apps/identity-service/src/modules/auth/`
- `apps/content-service/src/modules/topics/`
- `apps/assessment-service/src/modules/scoring/`

Each will have pattern: `*.module.ts`, `*.controller.ts` (HTTP routes),
`*.service.ts` (business logic), `*.repository.ts` (Prisma queries).

#### `prisma/schema.prisma` — the database's "design + migration tool"

Prisma = the ORM. `schema.prisma` is the **single source of truth**
listing tables. Generated client gives type-safe queries
(`prisma.user.findMany()`). Run per-service — all four now share ONE database
(conficircle_db) but each owns its own PostgreSQL schema, so identity
still can't query the content tables directly (schema isolation).

The FILE ITSELF:

```prisma
generator client { provider = "prisma-client-js" }   // codegen settings
datasource db     { provider = "postgresql"
                    url = env("IDENTITY_DATABASE_URL") }

model User { id String @id @default(uuid()) ... }
```

Models we defined (Reminder: drafts, no migrations run yet):

| Schema | Models |
| --- | --- |
| identity | `User`, `RefreshSession`, `GuestSession` |
| content | `Topic`, `Question`, `QuestionOption`, `QuickTip`, `VideoResource`, `LearningResource`, `ContentPublication` |
| assessment | `Assessment`, `AssessmentQuestion`, `AssessmentOption`, `AssessmentAttempt`, `AttemptResponse` |
| progress | `VideoProgress`, `TopicProgress`, `ActivityEvent`, `DailyStat` |
| + every domain DB | `OutboxEvent` (transactional outbox — see Part 5) |

Cross-service references (e.g. `VideoProgress.userId`) are just UUID
strings: **no foreign keys crossing databases** — intentional, per
Phase 5. Application code enforces that the referenced user exists
using events/HTTP, never raw joins.

#### `test/app.e2e-spec.ts` — "smoke test"

Uses `supertest` + `@nestjs/testing` to boot the real app in-memory and
fetch `/health`. We used it to prove each app actually initializes.

#### `Dockerfile` — the service's "own little machine"

Two-stage Dockerfile: a build stage (`node:20-alpine` + `pnpm` +
workspace source → `tsc`) and a thin production image copying the
compiled JS. Today only used if we ever `docker build`ing each app;
local dev runs straight on the host.

#### `jest.config.js` + `tsconfig.test.json`

Test runner wiring for ts-jest so `pnpm test` works in any app.

## Part 3 — The 4 shared packages in `packages/`

Shared code that every app needs. Think of these as the
"common lib". Each is a precompiled tiny TypeScript library with
`dist/index.js` consumed via `"@conficircle/<x>": "workspace:*"`.

### `packages/contracts/` — shapes of data crossing HTTP

Like Flutter's model classes; keeps gateway and backend type-consistent.
Interfaces: `PublicUserDto`, `TopicDto`, `QuestionDto`,
`SubmitAssessmentResponseDto` etc. Example: "gateway's compile breaks"
if you change a field on identity's login response so you must update
both.

### `packages/event-schemas/` — shapes of events crossing RabbitMQ

- `EVENT_EXCHANGE` name
- `EVENT_ROUTING_KEYS` constants: `identity.user.registered` etc.
- `EventEnvelope<T>`: exactly what a message body is
  `{eventId, eventType, occurredAt, producer, attempt, payload}`
- payload types: `UserRegisteredPayload`, `AssessmentCompletedPayload`…

### `packages/logger/` — logging you can actually grep

`createLogger({service})` returns a logger like Flutter's `print` but:

1. every line is a single JSON object (parseable by log tools)
2. includes `service`/`ts` automatically
3. redacts keys like `password`, `token`, `authorization`, etc. even
   if you accidentally log a secret
4. `asNestLoggerService()` adapter makes Nest's own log system use it

### `packages/configuration/` — env validation helpers

Currently `BaseEnv` class (class-validator decorators), plus small
utilities (`parseOrigins`, constants). As real features grow, each
service's env validation will build on it.

## Part 5 — Cross-cutting concepts you must learn

### 1. Database-per-service (why 4 databases in one PG?)

A "database" in PG is a namespace with an address. Sharing ONE db means
anyone can accidentally query the other's tables → tight coupling.
Separate DBs force the boundary. One PG *container* is a money/dev
convenience; production would likely have 4 containers, no code change.

### 2. Correlation IDs (the tracing trick)

`.x-request-id` attached at the gateway, echoed by every service +
every log line. When someone emails "the app is broken at 2am", grep
once instead of scrolling five log files.

### 3. JWT + refresh (auth on a map)

- login → get 2 tokens
  - **access token** — 15 min; sent with every request
  - **refresh token** — 30 days; used ONLY to get new access tokens,
    stored hashed in RefreshSession for revocation
- rotation: each refresh invalidates the old one (if an old one shows
  up twice → suspicious)
- guest: same table `GuestSession` with quota; conversion event fired
  when they sign up.

### 4. Transactional outbox

Problem: "AssessmentCompleted saved" + "event fired" can't be one
operation — if you insert then crash before the publish, data lives but
the world doesn't know. Outbox: insert a row in the same transaction to
an `OutboxEvent` table; a serializer polls and publishes. This is
wired in each schema but no code uses it yet.

### 5. Auth at the gateway vs in each service

Gateway validates the token and forwards identity so it's not done
twice, but **domain services ALWAYS re-enforce ownership** ("is this
attempt really this user's?") — never trust an upstream "trust, I
already checked."

### 6. Why Prisma per-app and not a shared "DB package"

Sharing a `prisma/client` package would silently let app A read app B's
tables. Keeping them separate physically enforces the ownership rule.

## Part 7 — Cheat sheet: which file when X breaks

| --- | --- |

## Part 8 — Glossary

- **Monorepo**: one repo with many build-able projects sharing a node_modules.
- **Microservice**: independent deployable service with a bounded domain.
- **API Gateway**: public entry point of microservices; one entrance; no logic.
- **ORM (Prisma)**: write TS, Prisma makes SQL for you.
- **Migration (outbox, above)**: transactional journal ensuring events
  aren't lost meanwhile.
- **DLQ**: parking lot for messages that failed too many times.
- **Idempotency**: applying the same event twice changes nothing —
  the result is one click, not two.
- **SCAFFOLD vs FEATURE**: the frame of a house vs installing its wiring.
 You have the frame today.
